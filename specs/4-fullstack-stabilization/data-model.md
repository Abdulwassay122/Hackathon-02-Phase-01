## Overview

This data model represents the entities and relationships for the Todo application that need to be properly integrated between frontend and backend. The focus is on ensuring consistent data flow and proper handling of entities across the full-stack application.

## Data Relationships

### 1. User-Task Relationship
- **Relationship Type**: One-to-Many (One User to Many Tasks)
- **Foreign Key**: `user_id` in Task table references User
- **Access Pattern**: Each user can access only their own tasks
- **Authorization**: Backend enforces user-specific data access

### 2. Authentication-Task Relationship
- **Relationship Type**: Token-based access control
- **Access Pattern**: JWT token contains user_id to filter tasks
- **Authorization**: Frontend includes JWT in request headers
- **Validation**: Backend validates token and checks user_id matches requested data

## Data Validation Rules

### 1. Task Validation
- **Title**: Required, minimum 1 character, maximum 255 characters
- **Description**: Optional, maximum 1000 characters
- **Completed**: Boolean, defaults to false
- **User ID**: Required, must match authenticated user
- **Timestamps**: Auto-generated by backend

### 2. API Response Validation
- **Success Flag**: Required boolean indicating operation success
- **Data**: Present when operation succeeds, null when fails
- **Error**: Present when operation fails, absent when succeeds
- **Message**: Optional human-readable message

## Data Storage

### 1. Database Schema
```sql
-- Tasks table
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title VARCHAR(255) NOT NULL,
  description TEXT,
  completed BOOLEAN NOT NULL DEFAULT 0,
  user_id VARCHAR(255) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id)
);
```

### 2. Indexing Strategy
- **User ID Index**: For efficient user-specific task queries
- **Created At Index**: For chronological task ordering
- **Completed Index**: For filtering completed/incomplete tasks

## Data Security

### 1. Access Control
- **User Isolation**: Users can only access their own tasks
- **JWT Validation**: All requests validated against user token
- **Database Filtering**: Backend filters results by user_id

### 2. Data Protection
- **Input Sanitization**: All inputs validated and sanitized
- **SQL Injection Prevention**: Parameterized queries used
- **Token Validation**: JWT tokens verified before data access

## Data Consistency

### 1. Synchronization
- **Frontend-Backend**: Data models kept in sync between systems
- **Timestamps**: Backend generates consistent timestamps
- **Validation**: Same validation rules applied on both sides

### 2. Error Handling
- **Validation Errors**: Consistent error response format
- **Network Errors**: Graceful degradation in frontend
- **Conflict Resolution**: Last-write-wins for concurrent updates

## API Endpoints and Data

### 1. Task Endpoints
- **GET /api/tasks**: Retrieve user's tasks → Returns Task[]
- **POST /api/tasks**: Create new task → Returns Task
- **PUT /api/tasks/{id}**: Update task → Returns Task
- **DELETE /api/tasks/{id}**: Delete task → Returns null

### 2. Authentication Endpoints
- **GET /api/auth/me**: Get current user → Returns User
- **POST /api/auth/login**: User login → Returns JWT token
- **POST /api/auth/logout**: User logout → Returns success response

## Data Transformation

### 1. Backend to Frontend
- **Date Format**: Python datetime → ISO string
- **Boolean Format**: Python bool → JSON boolean
- **Error Format**: Python exception → API response

### 2. Frontend to Backend
- **Date Format**: ISO string → Python datetime
- **Boolean Format**: JSON boolean → Python bool
- **Validation**: TypeScript interfaces → Python validators
