# Research: Fix Task API 401 Authentication & Migrate DB to Neon PostgreSQL

## Investigation Summary

This research investigates the current authentication implementation and database setup to understand the root causes of the 401 authentication errors and SQLite usage, despite PostgreSQL configuration.

## Current State Analysis

### Authentication Issues
- Current backend uses Better Auth for JWT generation
- Authentication middleware in `backend/src/auth/middleware.py` needs to properly validate JWT tokens
- Task API endpoints in `backend/src/api/tasks.py` require proper user identification from JWT
- The JWT validation process needs to:
  1. Extract token from `Authorization: Bearer <token>` header
  2. Verify token signature using `BETTER_AUTH_SECRET`
  3. Decode user information (ID, email) from token payload
  4. Compare authenticated user ID with requested resource user ID

### Database Configuration
- Current database connection in `backend/src/database/connection.py` uses SQLite
- PostgreSQL migration requires:
  1. Update connection string to use `DATABASE_URL` environment variable
  2. Modify SQLModel engine creation to use PostgreSQL driver
  3. Ensure table creation works with PostgreSQL
  4. Verify task data persistence after migration

## Decision: JWT Validation Approach
- **Rationale**: Need to implement proper JWT validation that matches the token format generated by Better Auth
- **Implementation**: Use PyJWT library to decode and validate tokens, extracting user ID from the payload
- **Alternatives considered**:
  - Direct Better Auth integration (would require more complex setup)
  - Custom token validation (would be error-prone)

## Decision: Database Migration Strategy
- **Rationale**: Moving from SQLite to PostgreSQL for production readiness
- **Implementation**: Update database connection factory to read from `DATABASE_URL` environment variable
- **Alternatives considered**:
  - Keeping SQLite (not suitable for production)
  - MongoDB or other databases (would require major schema changes)

## Decision: User Enforcement Method
- **Rationale**: Prevent users from accessing tasks that don't belong to them
- **Implementation**: Extract user ID from JWT and filter all task queries by this ID, compare with route parameters
- **Alternatives considered**:
  - Client-side enforcement only (not secure)
  - Role-based access control (overkill for this use case)

## Technical Requirements Identified

### For JWT Implementation
1. Import `jwt` module (PyJWT) for token decoding
2. Retrieve `BETTER_AUTH_SECRET` from environment variables
3. Create middleware function to extract and validate tokens
4. Update API routes to accept user ID from validated tokens

### For Database Migration
1. Install PostgreSQL driver (e.g., psycopg2-binary)
2. Update requirements.txt with PostgreSQL dependencies
3. Modify connection.py to use DATABASE_URL
4. Test table creation and data persistence in PostgreSQL

### For User Enforcement
1. Update all task endpoints to require user ID validation
2. Implement user ID comparison logic
3. Return appropriate HTTP status codes (401, 403) for invalid access attempts
4. Update API documentation to reflect new authorization requirements

## Key Findings

### Authentication Flow
1. Frontend receives JWT from Better Auth upon login
2. Frontend attaches JWT to API requests in Authorization header
3. Backend middleware extracts and validates JWT
4. Validated user ID is used to filter task queries
5. User ID from JWT is compared with route/user parameters for enforcement

### Database Connection
1. Current connection uses SQLite file: `sqlite:///./todo.db`
2. Target connection will use: `postgresql://username:password@host:port/database`
3. Environment variable `DATABASE_URL` will contain the PostgreSQL connection string
4. Engine creation will use PostgreSQL dialect instead of SQLite

## Security Considerations
- JWT tokens must be validated server-side (never trust client claims alone)
- User ID comparisons must prevent access to other users' data
- Proper error responses must not leak sensitive information
- Secret keys must be managed through environment variables only
